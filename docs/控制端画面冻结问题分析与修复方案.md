## 二、架构事实：输入与画面是两条通路（症状 #1 的根源背景）

- **输入**：Dart → Rust 直接 FFI 调用（`session_send_mouse` 等）。不经过事件流，**永远不会被画面问题阻塞**。这解释了"能控制但画面不动"。
- **画面**：Rust → Dart 事件流，由**单个串行循环**处理（`flutter/lib/models/model.dart` ~3893 起），且带"单槽握手"协议：

```
Rust 视频线程（src/flutter.rs: on_rgba_soft_render）:
  若 display_rgbas[display].valid == true（上一帧尚未被 Dart 取走）→ 丢弃当前帧，return
  否则：交换缓冲 → valid = true → 发 EventToUI::Rgba(display)

Dart（model.dart: onRgba）:
  getRgbaSize / getRgba（裸指针拷贝）→ decodeImageFromPixels → update() 重绘
  → platformFFI.nextRgba() → valid = false（允许 Rust 发下一帧）
```

## 三、代码层分析：永久冻结的失败模式

### 3.1 原设计初衷（为什么这样设计）

`get_rgba`（src/flutter.rs:1088）返回的是**裸指针**（`data.as_ptr()`），不做拷贝，Dart 跨 FFI 直接搬 ~8MB 数据。`valid` 标志身兼三职：

1. **裸指针生命周期护栏（最关键）**：`valid == true` 期间视频线程绝不 swap/写缓冲；Dart 搬完字节调用 `next_rgba` 置 false 后，缓冲才允许被解码器复用。全程无锁，安全契约全靠这个握手。
2. **最新帧语义（vsync 式）**：单槽信箱，只渲染最新画面，旧帧丢弃——Dart 慢时不会越拖越远。
3. **内存上界**：每显示器仅一个 ~8MB 缓冲交换复用，无队列堆积，30fps 不会灌爆 Dart 事件循环。

### 3.2 冻结失败模式（已从代码证实）

只要 Dart 侧**任何一次**没有走完 `next_rgba`，`valid` 永远停在 `true`，此后每一帧都被 Rust **静默丢弃**（flutter.rs:1204 `return`，无日志、无计数、无自愈）。可能的触发点：

- **首帧初始化链**（`update()` 中 `_image == null` 时串行 await 4 个 FFI 往返：
  `updateViewStyle` → `updateScrollStyle` → `initializeEdgeScrollEdgeThickness` → `initializeCursorAndCanvas`），
  任一环节挂起即卡死整个后续帧流；
- `decodeImageFromPixels` 长时间不返回；
- 事件循环被某个 Event 处理器长期占用。

该失败模式与症状 #1 完全吻合（输入正常 + 画面永冻 + 重启复位 + 偶发自愈）。

**注意**：目前没有实证每一次冻结都是该机制触发——日志零痕迹正是问题所在，这正是方案 A 要补的。

### 3.3 症状 #2（纯黑屏）的另一成因

会话连接失败（Connection closed）后，**会话窗口不会自动关闭**，残留一个纯黑窗口。
10-28 17:25 的"黑屏"实为探测失败后的残留窗口（AppleScript 确认窗口存在但会话已死）。

## 四、网络层排查结论（10-27 ~ 10-28）

与代码无关、但同样导致"卡连接/画面不动"的独立因素，按时间线：

1. **盒子网络三连换、次次注册断续**：192.168.1.x（内网）→ 移动 223.104.110.66 → 10.10.14.x（wlan0）。
   每个网络上都出现 hbbs 侧 `Remote desktop is offline` / `IP change` 反复横跳（hbbs 日志 03:14、03:15 两次相隔 78 秒的 IP change）。
2. **网段冲突（已随盒子迁走消除）**：盒子曾在内网报本地地址 `192.168.1.102`，与 mac 自身 IP 完全相同
   （两边都是 192.168.1.x 网段）→ 本地地址打洞等于 mac 连自己，必败。
3. **hbbs"同公网出口"误判**：两侧公网出口相同时，hbbs 回 LocalAddr 走局域网直连分支。
   盒子在 10.10.14.x 时 hbbs 给出的是 SNAT 中间地址 `10.10.14.129`（非盒子真实 IP .116），直连依然失败。
   ⇒ 跨网场景**直连打洞不可用是常态，连通依赖中继**（中继链路已多次验证可用：11:27 配对存活 6 分半；17:36 中继 18ms 建立）。
4. **疑似 Android Doze**：盒子上观察到到 21116 的连接周期性重建（TIME_WAIT 残留）、17:47 一度零连接且 adb offline。
   建议给被控 app 关闭电池优化/保持前台，避免息屏后注册被掐。

## 五、候选修复方案（测试后二选一或组合）

### 方案 A：Rust 侧丢帧诊断日志（纯观测，零行为变更）

- **改动文件**：`src/flutter.rs`（`RgbaData` 结构体 + `on_rgba_soft_render`）
- **设计**：
  - `RgbaData` 增加字段：`drop_started_at: Option<Instant>`、`drop_count: u64`、`last_drop_logged_at: Option<Instant>`；
  - 丢帧分支：记录连续阻塞起始时间；**连续阻塞 ≥ 2 秒**才告警，且每 5 秒最多一条
    `WARN rgba of display N not fetched by flutter for Xs (M frames dropped)`；
  - 恢复取帧时：`INFO ... resumed after Xs (M frames dropped)` 并清零。
- **为何用"连续阻塞时长"而非计数**：最新帧语义下正常负载也会合法丢帧（Dart 渲染 100ms 时 30fps 约丢 20 帧/秒），
  按计数会日常误报；按连续时长只在真冻结时发声。
- **风险**：零（纯日志）。日志量可控（5 秒限流）。
- **能回答的问题**：再冻结时，日志直接区分"帧被丢弃"（Dart 侧卡死 → 方案 B 适应症）vs"根本没有帧"（盒子采集/编码或链路问题）。

### 方案 B：Dart 侧超时自愈（行为变更，最小侵入）

- **改动文件**：`flutter/lib/models/model.dart`（`onRgba`，~1949 行）
- **设计**：`decodeAndUpdate` 包 `.timeout(Duration(seconds: 3))`，`TimeoutException` 与现有 catch 合并处理，
  保证 `nextRgba` **必然**被执行（成功/异常/超时三条路都归还缓冲）。
- **风险分析**：
  - Rust 侧一行不动，`valid` 仍只由 `next_rgba` 复位——裸指针安全契约完整；
  - 被放弃的迟到解码若最终完成，会回写一帧旧图（约 33ms 后被新帧覆盖，不可感知；已有 `parent.target?.id != pid` 守卫防串会话）；
  - 超时参数 3 秒：远大于正常解码耗时，慢机器上也几乎不会误触发。
- **效果**：Dart 偶发卡死时画面最多停 3 秒自愈，不再需要重启客户端。
- **注意**：`model.dart` 为两端共享代码，需同时重发 mac 与 APK（但被控端无 UI 不走此路径，实际只影响控制端行为）。

### 方案 C：`get_rgba` 改为 Rust 侧拷贝返回（彻底，改动大）

- 消灭裸指针后，Rust 侧超时覆盖才真正安全。需改 FFI 签名并重新生成 bridge_generated，
  涉及 `src/flutter_ffi.rs` 与生成链路，非必要不做。

### 推荐组合与决策标准

```
第一步：上方案 A（观测），正常使用直到再次冻结
第二步：看日志裁决
  - 出现 "not fetched by flutter for Xs" 后自愈/持续  → 确认 Dart 卡死 → 上方案 B
  - 无该日志但画面冻 → 帧根本没到 mac → 查盒子采集/编码/链路（与代码无关）
  - 若日志显示频繁小幅阻塞（1~2 秒级）→ 属正常背压，勿误判为故障
```

| 文件 | 位置 | 内容 |
|------|------|------|
| `flutter/lib/main.dart` | `kIdServer` / `kRelayServer` / `kServerKey`（~142 行） | 控制端+有 UI 场景，启动时强制写 |

- mac 端：`cargo build`（见下方环境变量）+ `flutter build macos` + `codesign --force --deep --sign -` 重签；
- Android 端：其 `librustdesk.so` 来自 `flutter/android/app/src/main/jniLibs/arm64-v8a/` 预编译产物，
  若 Rust 侧有改动需 `cargo ndk` 交叉重编并更新 jniLibs，否则仅 `flutter build apk` 即可。

**mac 端 Rust 重编必需环境变量**（本机 Xcode 27 + Rust strip 已知问题）：

```bash

VCPKG_INSTALLED_ROOT="$PWD/vcpkg_installed" \
CARGO_PROFILE_RELEASE_STRIP=none \

```

（`strip=none` 规避 rust-lang/rust#157750：macOS 剥离 debuginfo 产出 LINKEDIT 字符串池错位的 dylib，被 Xcode 15+ 链接器拒收。）

## 八、结论摘要

1. "重启 mac 客户端才能恢复的画面冻结"存在真实的代码层失败模式（单槽握手无超时、无日志、无自愈）；
2. 但 10-27/10-28 的多次连接失败主因是**被控盒子网络注册断续**（三个网络均复现），mac 侧全程零解码失败；
3. 建议先上方案 A 取证，再按第五节决策标准决定是否上方案 B；方案 C 暂缓。

### 9.2 实锤根因：hbbs 防劫持死锁（"打洞静默"的直接原因）

hbbs（自研定制版，`/var/log/rustdesk/hbbs.log`，sqlite 库 `db_v2.sqlite3`）的防 ID 抢占机制：
**pk 与注册 IP 同时变化**的 register_pk 一律回 `UUID_MISMATCH` 且**库中记录一字不改**。

盒子 `pm clear` 重生成了密钥对（pk 变），又被搬到现场（出口 IP 171.15.17.109 → 115.57.53.176 变），
"双变"命中死锁：库中记录停在旧地址 → punch 包转发进黑洞 → 盒子收不到 → 不回 PunchHoleSent →
hbbs 无兜底响应 → mac 端 18 秒静默超时。客户端表现即"正在连接/黑屏"。

- 对照组：DWDEV202503260023 同日三次换网只变 IP，`update_pk` 全部自动放行——机制本身正常；
- 唯一性：`ro.serialno = DWDEV202401090905`，ID 派生自串号，排除同 ID 双实例；
- **清理流程**（已执行，库备份 `db_v2.sqlite3.bak-20261029`）：
  ```bash
  systemctl stop rustdesk-hbbs
  sqlite3 /opt/rustdesk/db_v2.sqlite3 "delete from peer where id='DWDEV202401090905';"
  systemctl start rustdesk-hbbs   # 盒子 ~20s 内自动重注册（新 IP + 新 pk 落库）
  ```
- **运维规则**：只换网络 → 自动放行；`pm clear`/刷机 + 换网络同时发生 → 必现死锁 → 按上述流程清理。
  部署新 APK 一律 `install -r`，不要 pm clear。

### 9.4 已实施改进二：register_pk 重连退避（被控端注册层）
