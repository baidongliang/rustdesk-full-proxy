# RustDesk 资源占用与部署要求说明(实测 + 官方对照)

> 生成日期:2026-08-26
> 实测环境:被控端 192.168.1.116(DWD68 平板,4 核 / 4GB RAM / Android 11,SN `DWDEV202401090814`);
> 控制端 mac mini(LAN 直连);服务端 39.105.73.125(2 vCPU / 1.87GB RAM,阿里云,hbbs/hbbr 单实例)

---

## 快速总结(一句话版)

**被控端可以忽略不计,服务端闭眼买最低配、把预算留给带宽。**

- **被控端(实测,4核/4GB 安卓平板)**:待命 CPU ~1% / 内存 50MB,常驻无感;被控时 CPU ~16% / 内存 72MB / 带宽 ~0.1Mbps(静止画面,动态最多 ~3Mbps)。设备毫无压力,**2核2G 的安卓设备就够跑,4核更稳**。
- **服务端**:1核1GB 即可带约 1000 并发中继连接;现有 2核2G 用量接近零(内存合计 <10MB、CPU ≈0%)。**带宽是唯一要花钱的**——只在中继(跨网段直连失败)时消耗,每路 0.1~3Mbps;同网段设备全直连、服务器零流量。选型:50 台内 → 1核1G/5M 随便跑;几百台 → 2核2G,带宽按"同时中继路数 × 3Mbps"往上加。

## 一、Android 被控端实测(本项目定制无 UI 版)

### 1.1 三种状态资源占用

| 状态 | CPU(四核总量) | 内存 PSS | 网络 | 说明 |
|---|---|---|---|---|
| **空闲待命**(已注册,无会话) | **~1%** | **50MB** | 每 16s 一个注册心跳 UDP 包 + 18s 一次 21114 心跳重试 | 常驻前台服务;占 4GB 设备内存约 1.2% |
| **受控中**(LAN 直连,VP8,静止画面) | **16%**(≈0.64 核) | **72MB** | **上行 ~90kbps** 视频流 | 软件编码(`hardware: false`)是 CPU 主要开销 |
| **会话结束** | **≈0%**(线程全部睡眠) | 秒级回落 50MB | — | 会话拆解干净,无泄漏 |

注:
- 视频码率随画面内容变化大:官方口径 1080p 中继会话在 **30KB/s ~ 3MB/s** 之间,办公场景典型 ~100KB/s;播放视频/动画时可到 1~5Mbps。静止画面实测 ~11KB/s(90kbps)属正常低值。
- `top` 进程级 CPU 列为开机以来均值,判断实时占用请用线程级采样(`top -H`)或 `dumpsys cpuinfo` 前后对比。
- CPU 16% 的主因是**纯软件 VP8 编码**;该平台硬编不可用(日志 `usable: h264=false, h265=false`)。若换硬编平台可大幅下降。
- 21114 心跳重试(Pro 版 API 端口,OSS 无)每 18s 两次 TCP 尝试,CPU/流量开销可忽略,仅日志噪音。

### 1.2 与业务 app 共存

被控端空闲态(1% CPU / 50MB)与书柜业务 app(MQTT 心跳 + 界面)同机运行无感知冲突;受控时 CPU 升高属临时性,会话结束即回落。

## 二、客户端官方要求(Win / macOS / Android)

**官方未发布正式的最低配置表**,仅定性说明"硬件要求非常低"。平台支持情况([官方客户端文档](https://rustdesk.com/docs/en/client/)):

| 平台 | 支持情况 | 备注 |
|---|---|---|
| Windows | ✅ 完整 | 便携版免安装、免管理员权限 |
| macOS | ✅ 完整 | 控制需辅助功能/屏幕录制权限 |
| Linux | ✅ | Ubuntu≥16 / CentOS / Fedora≥18 等 |
| Android | ✅ 完整 | 可作控制端;作被控端需无障碍权限(本项目即此用法) |
| iOS | ⚠️ 仅控制端 | 系统限制无法被控 |
| Web | ✅ 免安装控制 | |

实践口径(社区经验):近十年内任意 x86/ARM 设备均可流畅运行;被控端开销主要在**视频编码**(取决于分辨率/帧率/内容,以及有无硬件编码),控制端主要在**视频解码**。本项目实测与该口径一致(4 核 4GB Android 11 被控完全够用)。

## 三、服务端部署要求(hbbs/hbbr)

### 3.1 硬件要求([官方安装文档](https://rustdesk.com/docs/en/self-host/rustdesk-server-oss/install/))

官方口径:**"硬件要求非常低,最低配云服务器即可"**;FAQ/社区经验:**1 vCPU + 1GB RAM 可支撑约 1000 个并发中继连接**。

- **hbbs**(ID/注册服务器,21115/21116 TCP+UDP):只做注册、打洞信令、密钥交换——极轻量,内存几 MB 级
- **hbbr**(中继服务器,21117 TCP):纯网络转发,IO 型负载,CPU 占用极低;内存几 MB 级

**本项目服务器实测**(2 vCPU / 1.87GB,当前 5 台设备注册):

| 进程 | CPU | 内存 RSS |
|---|---|---|
| hbbs | ~0% | 6MB |
| hbbr | ~0% | 2MB |

### 3.2 带宽要求(核心瓶颈)

**带宽才是服务端的主要成本**,且只在**中继会话**时产生——P2P 直连成功的会话完全不经过服务器(本项目同网段设备全部直连,服务器带宽消耗为零)。

| 场景 | 单会话带宽 | 说明 |
|---|---|---|
| 办公/静止画面 | ~100KB/s | 常见远程办公 |
| 一般动态画面 | 0.5~2Mbps | |
| 1080p 高动态上限 | ~3MB/s(24Mbps) | 视频播放类内容 |

### 3.3 不同规模的服务器选型建议

| 设备规模 | 同时活跃中继会话 | 建议配置 | 带宽 |
|---|---|---|---|
| <50 台(当前阶段) | <10 | 1C1G | 5Mbps |
| 50~500 台 | 10~100 | 2C2G | 10~50Mbps |
| 500~2000 台 | 100~500 | 4C4G | 50~200Mbps,可拆多 hbbr 节点 |
| 更大/跨地域 | — | 多节点 + [Pro 版地理路由](https://rustdesk.com/docs/en/self-host/rustdesk-server-pro/relay/) | 按区域分布 |

注:OSS 版为单 hbbs 单点,不支持集群;规模上去后考虑 Pro 版(多 hbbr 中继节点、按地理位置就近路由)或自建调度。

### 3.4 带宽控制参数(hbbr 环境变量,参考 [rustdesk-server#104](https://github.com/rustdesk/rustdesk-server/issues/104))

| 变量 | 默认值 | 作用 |
|---|---|---|
| `SINGLE_BANDWIDTH` | 128 Mb/s | 单个中继连接上限 |
| `TOTAL_BANDWIDTH` | 1024 Mb/s | 总带宽上限 |
| `LIMIT_SPEED` | - | 限速(Mb/s) |

小带宽 VPS 可下调(如 `SINGLE_BANDWIDTH=16`)防止单会话打满。

## 四、对照结论

1. **被控端(Android)**:空闲 1% CPU / 50MB 内存,常驻无压力;受控时 CPU ~16%(软编所致)在 4 核设备上完全可接受。官方无正式配置表,实测 4C/4G 远超实际需要,**2C/2G 的入门 Android 设备即可承载**(软编下建议至少 4 核以保证流畅)。
2. **控制端(mac/Win)**:开销主要在解码,现代机器无压力;官方口径任意近十年设备可用。
3. **服务端**:当前 2C/2G 阿里云 + 5 台设备,hbbs/hbbr 合计 <10MB 内存、CPU ≈0,**余量巨大**;真正的扩展瓶颈是**中继带宽**(仅跨网段会话产生)。当前规模下无需扩容;上百台跨网并发时按 §3.3 表扩带宽或加 hbbr 节点。
4. 本项目特有的两项开销均无害:被控端 21114 心跳失败重试(日志噪音)、同网段全部直连(服务器零流量)。

## 五、安全分析(控制链视角)

### 5.1 控制链全景

```
控制端(mac/Win)                          被控端(Android,无 UI)
   │  注册/信令(UDP·TCP 21116)              │ 开机自启 → 注册(ID=SN,uuid=SN派生)
   └──────────────→ hbbs(39.105.73.125) ←──┘    信令由服务器私钥签名,客户端以 kServerKey 验证
                          │ 打洞协调
   ←──── 数据面 ────────→ │
   ├─ P2P 直连(同网段/打洞成功,E2E 加密)
   └─ hbbr 中继(TCP 21117,只见密文 + 流量元数据)
```

**加密体系**:每端本地生成 ed25519 密钥对,公钥(pk)登记在 hbbs;控制端连接时从 hbbs 取对端 pk,建立 NaCl(xsalsa20poly1301)端到端加密会话——中继服务器与 hbbs 均无法解密会话内容。

### 5.2 各端技术风险清单(实测核实)

**被控端(Android)**

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| R1 | 密码 = SN 数字,无独立熵 | 中 | 知道 ID 即知道密码(ID 公开于设备标签/ThingsBoard);内网可控环境的设计权衡 |
| R2 | SN 不合规设备回落密码 `00000000` | 低 | 可猜;仅影响 SN 异常的少量设备 |
| R3 | 无人值守 approve-mode=password | 低 | 密码对即放行,无二次人工确认 |
| **R4** | **网络 adb 常开且未认证 + SELinux Permissive** | **高** | **实测 `ro.adb.secure` 为空、5555 常开、`getenforce=Permissive`:局域网内任何机器 adb connect 即可完全接管设备(装应用/读数据),权限远超 RustDesk。量产必须:关闭网络 adb 或 `ro.adb.secure=1`,SELinux 切 Enforcing** |
| R5 | 持有 WRITE_SECURE_SETTINGS 高权限 | 低 | app 可改任意 secure 设置;权限已最小化使用(仅无障碍自愈) |
| R6 | dewod"安全程序"口令 `Dewod1234` 硬编码且全局共享 | **中(系统级)** | 任意第三方 app 用同口令调 SDK 注册即可获得**投屏授权自动确认**→ 可静默投屏。建议推动 dewod 改为设备唯一口令或调用方签名校验 |
| R7 | 密码哈希+salt 存本地 toml | 低 | root/adb 可读(在 R4 面前已无独立意义) |

**控制链路(网络传输)**

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| R8 | E2E 加密可靠,中继仅见密文 | — | 但 hbbr/hbbs 可见**流量元数据**(谁连谁、时长、流量) |
| R9 | 首连 TOFU 窗口 | 低 | 被控端出厂首启即从代码兜底写入 kServerKey,窗口极小;控制端每次启动强制覆盖 key(注意防客户端被替换) |
| R10 | 局域网直连暴露面 | 低 | 被控端监听端口可被内网扫描直连(仍需密码+密钥双重验证,配合 R1 风险叠加) |
| R11 | 被控端公钥不匹配告警 | — | 被控端重置/被冒名时控制端会提示 key mismatch——**运维必须停止连接核查,不可盲点信任**(见 R13) |

**服务端(hbbs/hbbr)**

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| R12 | 注册无认证,可 ID 抢注 | 中 | hbbs 地址+key 可从 APK 提取;攻击者可抢先注册目标 SN(造成真实设备 UUID_MISMATCH 无法上线=DoS),或注册垃圾 ID 滥用资源。OSS 版无注册管控,规模大时考虑 Pro 版/API 管控 |
| R13 | 公钥替换攻击(配合 R12) | 中 | 抢注后控制端连接会遇 pk 不匹配告警——若运维习惯性"信任",会话即被劫持(E2E 下攻击者持自己密钥完成会话) |
| R14 | ssh root@ 公网 22 端口 | 中 | 已用密钥认证;建议加 fail2ban/改端口/源 IP 白名单 |
| R15 | 服务器私钥 id_ed25519 泄露风险 | 低 | 泄露可伪造信令签名(E2E 下仍难解密内容,但可劫持会话建立/做 R13) |
| R16 | db_v2.sqlite3 明文存 uuid/pk | 低 | 公钥本身非敏感,但可枚举在册设备 |

**控制端(mac/Win)**

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| R17 | TB 账号密码、hbbs 地址+key 硬编码 | 中 | 可从客户端产物提取,放大 R12 攻击面;正式版建议配置下发 |
| R18 | 控制端失守即持"万能钥匙" | 中 | 控制端机器被攻破 + R1 弱密码 = 全设备可达;重要场景启用 2FA |

### 5.3 与 RustDesk 官方安全机制的对照

| 官方机制 | 本项目状态 |
|---|---|
| 端到端加密(NaCl) | ✅ 默认启用 |
| 服务器 key 固定验证(kServerKey) | ✅ 已硬编码固定 |
| 密码哈希+salt 本地存储 | ✅ 启用 |
| 公钥不匹配(mismatch)告警 | ✅ 生效(依赖运维不盲信) |
| 2FA(TOTP) | ❌ 未启用 |
| IP 白名单(仅允许指定控制端连接) | ❌ 未启用 |
| 独立强密码 | ❌ 使用 SN 派生(设计权衡) |

### 5.4 缓解建议(按优先级)

1. **【量产必做】关闭设备网络 adb / `ro.adb.secure=1` / SELinux Enforcing**(R4——当前最大风险,与 RustDesk 无关但危害最大)
2. **推动 dewod 修复安全程序口令机制**(R6,设备唯一口令或签名校验)
3. 密码独立化(TB 每设备随机下发)或过渡期启用 **2FA + IP 白名单**(R1/R3/R18)
4. 服务器加固:ssh fail2ban/改端口/源白名单;规模上来后评估 Pro 版注册管控(R12/R14)
5. 运维规范:控制端遇**公钥不匹配告警必须中止连接核查**(R11/R13)
