# 被控端静默授权方案

> 本文记录 RustDesk 被控端在 Android 定制设备上**跳过用户授权弹框**的完整方案。
> 适用场景：被控端运行于拥有 root 权限的 Android 定制设备（dewod 系统，rk3568_r，Android 11 / SDK 30）。
> 配套设计文档：[`CUSTOM_HOST_DESIGN.md`](./CUSTOM_HOST_DESIGN.md) 第五章「静默授权方案」。

---

## 一、背景：为什么需要静默授权

RustDesk 被控端在 Android 上要正常工作，需要两类用户授权：

| 授权类型 | 作用 | 默认行为 | 阻塞点 |
|---------|------|---------|--------|
| **MediaProjection**（投屏） | 捕获屏幕画面送给控制端 | 弹出系统授权框 `MediaProjectionPermissionActivity`，需用户点"开始" | 设备屏幕无人操作，框卡住 → 投屏无法启动 |
| **AccessibilityService**（输入注入） | 把控制端的鼠标/键盘/触摸注入为设备操作 | 用户需进系统设置手动开启无障碍服务 | 设备无人操作，无法开启 → 控制端无法操控设备 |

定制设备是**无人值守**的（屏幕只跑业务 app），无法人工点授权框。因此必须让被控端**免人工**获得这两项授权。

## 二、实测环境

```
设备型号: DWD68 (rk3568_r)
Android 版本: 11 (SDK 30, userdebug build)
系统: dewod 定制系统 (eng.dewod.20240820.182823)
root: 可用 (adb root 后 shell uid=0；su 在 /system/xbin/su)
SDK: dewodSDK_1.0.03_release.aar
被控端包名: cn.xinzx.rustdesk.android
```

关键能力确认（实测）：
- `adb root` → shell 变 root（uid=0）
- `adb shell su -c "..."` → root 执行命令
- `adb shell settings put secure ...` → 可写系统 Settings
- `adb shell appops set ... allow` → 可改 AppOps
- **app 进程内 `Runtime.exec("su")` → 无权限**（Android 的 su 只允许 shell/adb uid 调用，app uid=10131 调用会被拒）

## 三、MediaProjection 投屏授权（已解决 ✅）

### 3.1 原始流程（弹框）

```
MainService.requestMediaProjection()
  → startActivity(PermissionRequestTransparentActivity)
    → mediaProjectionManager.createScreenCaptureIntent()
      → startActivityForResult(...)           ← 系统弹出 MediaProjectionPermissionActivity
        → 用户点"开始"
          → 返回带 token 的 Intent
            → MainService.getMediaProjection(RESULT_OK, data)
              → mediaProjection 就绪，media:true
```

`createScreenCaptureIntent()` 返回的 Intent 必须经过 SystemUI 的授权 Activity，普通 app 无法绕过。

### 3.2 尝试过的方案与结果

| 方案 | 做法 | 结果 |
|------|------|------|
| ① `appops set PROJECT_MEDIA allow` | adb root 设 AppOps | **框仍弹**，但定制系统会自动确认 → `media:true` 稳定 |
| ② Manifest 声明 `CAPTURE_VIDEO_OUTPUT` + `pm grant` | 运行时授予系统权限 | **失败**：`not a changeable permission type`（install-time 权限，不能运行时授予，需系统签名预装） |
| ③ 反射调 `MediaProjectionManager` 内部方法 | 跳过 `createScreenCaptureIntent` | 不稳定，Android 11 隐藏 API 限制，放弃 |
| ④ 自动点击授权框（root `input tap`） | 检测框弹出后用 `su -c input tap` 点"开始" | 代码已写入 `MainService.autoClickProjectionConsent()`，但 app 内 su 无权限，未触发 |
| ⑤ **`DwSecure.registerSafeProgram`**（SDK） | 注册为定制系统"安全程序" | **真正生效的机制**：注册成功后，定制 SystemUI 自动放行投屏授权 |

### 3.3 真正生效的机制

**核心结论**：定制设备上，被控端 app 调用 `DwSecure.getInstance(ctx).registerSafeProgram("Dewod1234")` 注册为"安全程序"后，定制系统的 SystemUI 会**自动确认** MediaProjection 授权框——框虽然会短暂弹出，但**无需人工点击**，约 5 秒内自动 `media:true`。

> 推测：定制 SystemUI 的 `MediaProjectionPermissionActivity` 检测到调用方是已注册的"安全程序"时，自动模拟确认按钮的点击。这是 dewod 定制系统的特性，标准 Android 无此行为。

### 3.4 配套代码改动（均已生效）

#### 3.4.1 `MainApplication.applySilentPermissions()`（root 双保险）
位于 `flutter/android/app/src/main/kotlin/com/carriez/flutter_hbb/MainApplication.kt`。

app 启动时异步尝试用 root 设置 `appops PROJECT_MEDIA allow`。在 app 内 su 实际无权限（日志 `silent perms skipped: no root`），但作为双保险保留——若未来 app 获得系统签名则自动生效。

```kotlin
private fun applySilentPermissions() {
    thread {
        if (!hasRoot()) {  // app 内通常无 root
            Log.i(TAG, "silent perms skipped: no root")
            return@thread
        }
        execRoot("appops set $pkg PROJECT_MEDIA allow")
        // ... 无障碍配置见第四章
    }
}
```

#### 3.4.2 `MainService.autoClickProjectionConsent()`（root 兜底）
位于 `flutter/android/app/src/main/kotlin/com/carriez/flutter_hbb/MainService.kt`。

`requestMediaProjection()` 触发后，起线程用 `uiautomator dump` + `su -c input tap` 自动点"开始"按钮。app 内 su 无权限时安静退出。

```kotlin
private fun requestMediaProjection() {
    startActivity(...)  // 原流程：弹授权框
    autoClickProjectionConsent()  // 新增：root 兜底自动点击
}
```

#### 3.4.3 Manifest 权限声明
`flutter/android/app/src/main/AndroidManifest.xml` 新增：
```xml
<uses-permission android:name="android.permission.CAPTURE_VIDEO_OUTPUT" />
<uses-permission android:name="android.permission.WRITE_SECURE_SETTINGS" />
```
声明在先，便于未来系统签名路径直接生效。

### 3.5 验证结果

清空所有授权后冷启动（零人工操作），连续测试：
```
appops PROJECT_MEDIA = ignore（清空）
settings enabled_accessibility_services = null（清空）
启动 app →
  registerSafeProgram(Dewod1234) -> true
  MainService onCreate
  ~5 秒后 → media:true   ← 投屏自动就绪
  [host-report] sn=..., rustdesk_id=...
```
**结论：MediaProjection 投屏授权框已成功跳过，`media:true` 稳定可靠。**

## 四、AccessibilityService 无障碍授权（部分解决 ⚠️）

### 4.1 原始流程（手动）

无障碍服务不能通过代码 `requestPermission` 申请，标准 Android 要求用户进**系统设置 → 无障碍**手动开启。

### 4.2 方案：root 写 `Settings.Secure`

Android 把"已启用的无障碍服务"存在两个 Secure Settings 里：
```
settings put secure enabled_accessibility_services "cn.xinzx.rustdesk.android/com.carriez.flutter_hbb.InputService"
settings put secure accessibility_enabled 1
```
root 下可直接写，免去用户手动开。

### 4.3 代码改动

#### 4.3.1 `MainApplication.applySilentPermissions()`（同 3.4.1）
app 启动时尝试 root 写无障碍配置（app 内 su 无权限时不生效）。

#### 4.3.2 adb 部署脚本预设（当前实际生效方式）
由于 app 内 su 无权限，无障碍配置目前通过 **adb（root shell）预设**：
```bash
adb shell settings put secure enabled_accessibility_services \
  "cn.xinzx.rustdesk.android/com.carriez.flutter_hbb.InputService"
adb shell settings put secure accessibility_enabled 1
```
可写入部署脚本，装机时一次性执行。

### 4.4 当前问题（待解决）

实测现象：
- `settings put secure enabled_accessibility_services` **写入成功**（`settings get` 能读到）
- InputService **`onServiceConnected` 触发过**（日志可见，服务连上了）
- 但随后 `dumpsys accessibility` 显示 `Crashed services:{InputService}`、`Binding services:{}`
- Flutter 层 `input:false`——服务绑定后又掉了

**判断**：InputService 绑定后立即崩溃/解绑。可能原因：
1. InputService `onServiceConnected` 初始化代码在定制系统上抛异常（如某些 AccessibilityService API 在 dewod 系统不可用）
2. 定制系统对第三方无障碍服务有限制（需把包名加入系统白名单）
3. `Crashed services` 是系统对"短时间多次 unbind"的误判

**影响**：仅影响**反向输入注入**（控制端鼠标/键盘操控设备），不影响投屏显示。控制端仍能看到设备画面，只是不能远程操控。

### 4.5 后续排查方向

1. 抓 InputService `onServiceConnected` 内部的异常（加 try-catch + 日志）
2. 确认定制系统是否有"无障碍服务白名单"机制（咨询 dewod 系统方）
3. 测试系统签名预装是否能解决无障碍绑定问题

## 六、部署/验证操作手册

### 6.1 一次性 root 与权限预设（装机时执行）

```bash
DEV=192.168.1.107:5555

# 1. 获取 root（userdebug build 才支持）
adb -s $DEV root
sleep 3
adb connect $DEV   # root 后需重连

# 2. 预设 AppOps（投屏自动放行的双保险）
adb -s $DEV shell appops set cn.xinzx.rustdesk.android PROJECT_MEDIA allow

# 3. 预设无障碍
adb -s $DEV shell "settings put secure enabled_accessibility_services \
  cn.xinzx.rustdesk.android/com.carriez.flutter_hbb.InputService"
adb -s $DEV shell "settings put secure accessibility_enabled 1"
```

### 6.2 验证静默授权是否生效

```bash
# 清空所有授权，模拟出厂状态
adb -s $DEV shell appops set cn.xinzx.rustdesk.android PROJECT_MEDIA ignore
adb -s $DEV shell "settings delete secure enabled_accessibility_services"
adb -s $DEV shell am force-stop cn.xinzx.rustdesk.android
adb -s $DEV logcat -c

# 启动被控端（零人工操作）
adb -s $DEV shell am start -n cn.xinzx.rustdesk.android/com.carriez.flutter_hbb.MainActivity
sleep 15

# 检查投屏是否自动就绪
adb -s $DEV logcat -d | grep "media, value: true"   # 应有输出 → 投屏 OK
adb -s $DEV logcat -d | grep "host-report"          # 应输出 sn + rustdesk_id
adb -s $DEV logcat -d | grep "registerSafeProgram"  # 应 -> true
```

### 6.3 状态查询命令

```bash
# 投屏 AppOps 状态
adb -s $DEV shell appops get cn.xinzx.rustdesk.android PROJECT_MEDIA
# 期望: allow

# 无障碍已启用服务
adb -s $DEV shell settings get secure enabled_accessibility_services
# 期望: cn.xinzx.rustdesk.android/com.carriez.flutter_hbb.InputService

# MediaProjection 当前是否有活跃会话
adb -s $DEV shell dumpsys media_projection | grep xinzx
# 期望: (cn.xinzx.rustdesk.android, uid=10131): TYPE_SCREEN_CAPTURE

# 无障碍服务绑定状态
adb -s $DEV shell dumpsys accessibility | grep -E "Binding|Crashed"
# 期望: Binding services 含 InputService（当前为 Crashed，见 4.4）
```

## 七、根因总结与关键认知

### 7.1 为什么 `appops set PROJECT_MEDIA allow` 单独不够？
AppOps 控制的是"操作是否允许"，但 `createScreenCaptureIntent()` 触发的授权框由 SystemUI 独立控制，AppOps 管不到 UI 弹框。真正让框"自动消失"的是 dewod 定制 SystemUI 对"安全程序"的放行逻辑。

### 7.2 为什么 app 进程内 `su` 无效？
Android 的 `su` 二进制（`/system/xbin/su`）只允许 shell（uid 2000）/adb 调用，普通 app（uid 1xxxx）调用会被 selinux/uid 检查拒绝。所以 `MainApplication.applySilentPermissions()` 在 app 内执行时日志是 `silent perms skipped: no root`。

→ **要 app 内有 root 能力，必须用系统签名预装**（获得 `SYSTEM` uid 或 platform 签名），这是 `CUSTOM_HOST_DESIGN.md` 第五章路径 1。

### 7.3 三层保险的生效情况

| 层 | 机制 | app 内生效？ | 当前作用 |
|----|------|------------|---------|
| 主 | `DwSecure.registerSafeProgram` + 定制 SystemUI 自动放行 | ✅ 是 | **投屏实际靠这个** |
| 辅 1 | app 内 `su` 设 appops | ❌ 否（app 无 root） | 失效但无害 |
| 辅 2 | app 内 `su` 自动点击框 | ❌ 否（app 无 root） | 失效但无害 |
| 部署 | adb root 预设 appops + 无障碍 | ✅ 是（装机执行） | 无障碍靠这个；投屏额外保险 |

### 7.4 下一步若要彻底无感
两条路二选一：
1. **系统签名预装**（`CUSTOM_HOST_DESIGN.md` 路径 1）：app 拿到 platform 签名后，`CAPTURE_VIDEO_OUTPUT` 自动获得，`createScreenCaptureIntent` 不再弹框，`WRITE_SECURE_SETTINGS` 可直接写无障碍。**最彻底，但需设备厂商配合签名**。
2. **保持现状**：投屏靠 `registerSafeProgram` 自动放行（已稳定），无障碍靠 adb 预设脚本（装机时执行一次）。**无需厂商配合，当前可用**。
