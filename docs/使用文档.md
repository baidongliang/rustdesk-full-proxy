# 定制版 RustDesk 使用文档

> 适用版本:1.4.9(分支 `master_dev`)
> 本文档描述本项目相对上游 RustDesk 的定制内容、部署步骤与日常使用方法。

## 一、项目概述

本项目基于 RustDesk 1.4.9 深度定制,用于对约 100 台跨公网分布的 Android 定制设备(DWD68 / rk3568,dewod 系统)进行集中远程管控,场景为无人值守设备运维。

与上游的主要差异:

| 定制点 | 说明 |
|---|---|
| 被控端无 UI 纯服务 | 独立 APK(`cn.xinzx.rustdesk.android`),开机自启,常驻后台,不显示任何控制端界面 |
| 设备 ID 与 SN 绑定 | ID 由设备序列号(SN)派生,重装/重启不变 |
| 密码自动派生 | 被控端自动以 SN 数字部分作为 permanent password,无需手工设置 |
| 服务器硬编码 | ID 服务器 / 中继服务器 / 公钥内置在客户端,清数据也不会注册到公共服务器 |
| Android IP 白名单 | 被控端内置连接方 IP 白名单,仅允许指定来源连接 |
| 静默授权自愈 | 投屏与输入注入免人工授权,崩溃/重启后自动恢复 |
| 三端 CI 打包 | GitHub Actions 自动构建 Android APK / macOS / Windows |

## 二、系统架构

```
┌─────────────────┐        ┌──────────────────────────┐        ┌──────────────────┐
│  控制端          │        │  自建服务器 111.6.173.14  │        │  Android 被控端   │
│  macOS/Windows  │◄──────►│  hbbs  (ID/注册, 21116)   │◄──────►│  无 UI 纯服务     │
│  Flutter 桌面端  │  P2P或  │  hbbr  (中继,    21117)   │  注册/  │  cn.xinzx.       │
│  设备列表 → 直连  │  中继   └──────────────────────────┘  中继   │  rustdesk.android│
└─────────────────┘                                                 └──────────────────┘
```

- **被控端**启动后向 hbbs 注册(ID = SN 派生值);控制端经 hbbs 协商连接,网络直连不通时走 hbbr 中继。同网段设备自动 P2P 直连,不经过服务器。
- **通信加密**:每端持有 ed25519 密钥对,端到端 NaCl 加密,服务器只见密文。
- **控制端**以设备列表为主入口,点击设备即按 SN 派生规则自动算出 ID 与密码直连;另支持 `rustdesk://connect?id=` deeplink 拉起。

## 三、核心机制

### 3.1 设备 ID:由 SN 派生

- SN 唯一来源:业务 app 经 `ProvisionService` 下发并持久化的本地缓存(Kotlin `SnHelper.kt` 只读该缓存)。不读取系统序列号;业务 app 从未下发 SN 即视为无身份。
- 无 SN 时:Rust 核心不启动、不产生随机 ID、不向 hbbs 注册(Kotlin 启动门控 + Rust 注册门控双保险),等待业务 app 拉起并下发;下发的缓存 SN 粘性有效,之后开机自启/打开 App 即直接注册。
- 派生规则(`libs/hbb_common/src/config.rs` 的 `sn_to_id()`):SN 归一化(仅保留字母数字 `_` `-`,转大写)后**原样作为 ID,不加任何前缀**,截断上限 32 字符。
  - 例:SN `202604260020` → ID `202604260020`(纯数字直接可注册;OSS rustdesk-server 仅校验长度 ≥6,不限制字符)。
- ID 与 uuid 均由 SN 派生,**跨重装、跨重启稳定**;若设备上已有旧随机 ID,启动时会自动迁移到 SN 派生 ID。

### 3.2 连接密码:由 ID 派生(v2)

- **被控端**:每次服务启动,以本机注册 ID(归一化后)经 HMAC-SHA256 派生 8 位密码,幂等写入 permanent password(`src/flutter_ffi.rs` + `libs/hbb_common/src/sn_password.rs`);ID 为空(未下发 SN)时跳过。
- **控制端**:设备列表按同一规则从目标 ID 派生密码自动填入(`flutter/lib/desktop/pages/device_list_page.dart` 的 `snDerivedPassword`),无需手输。
- 密码随 ID 同步变化(ID=SN,即随 SN 变化);部署密钥构建时注入,仓库内默认为公开测试密钥。
- 被控端 `approve-mode=password`:密码正确即放行,无人值守不弹确认框。

### 3.3 服务器配置(已内置)

客户端已硬编码以下配置,**无需(也不应)在界面上修改**:

| 配置项 | 值 |
|---|---|
| ID 服务器(hbbs) | `111.6.173.14`(端口 21116) |
| 中继服务器(hbbr) | `111.6.173.14:21117` |
| 公钥 Key | `rAwb4L6cuNQdHSEhQl4WYwWAMkClf78JZRHvMq0iLHM=` |

- 控制端(`flutter/lib/main.dart`)每次启动强制覆盖写入,防止被其他逻辑改动;
- 被控端无 UI 环境(`src/flutter_ffi.rs` `server_side`)在选项为空时写入兜底,同时兜底 `approve-mode=password`。

### 3.4 Android IP 白名单

被控端内置连接方白名单(`src/common.rs`),IP 不在列表内的连接会被拒绝("Your ip is blocked by the peer"):

```
111.6.173.0/25, 171.15.17.107, 171.15.17.108, 171.15.17.109, 192.168.0.0/16
```

即:服务器公网网段(中继/回调出口)、3 个固定控制端出口 IP、以及 `192.168.0.0/16` 局域网直连。设备上手工改过白名单则以手工值为准;清空后回落内置值。

## 四、被控端部署(Android)

### 4.1 安装 APK

1. 获取被控端 APK(CI 产物,包名 `cn.xinzx.rustdesk.android`,见 §6.1);
2. 安装到定制设备。应用无界面(启动后自动退到后台),仅通知栏有常驻前台通知;
3. 业务 app 已下发过 SN 的设备,开机自动拉起服务(BOOT_COMPLETED)并直接注册;从未下发 SN 的设备不自启也不注册,等待业务 app 经 ProvisionService 拉起并下发。

### 4.2 静默授权

被控端需要两项系统授权才能无人值守工作:

| 授权 | 实现方式 |
|---|---|
| 投屏(MediaProjection) | 首次部署需人工点击一次系统投屏授权框("立即开始");无人值守场景可由运维执行 root 模式脚本 `appops set <pkg> PROJECT_MEDIA allow` 预授权(重启持久,但重启后仍需一次授权框确认)。 dewod SDK 已移除(其 1.0.03 版缺 `DwSecureManager` 类,自动放行不可用) |
| 输入注入(AccessibilityService) | 写入 secure settings 启用无障碍服务;若服务曾崩溃,app 启动/开机时自动"先禁用再启用"清崩溃退避标记重新绑定 |

**部署脚本**(装机后执行一次,推荐):仓库内 `flutter/deploy_silent_perms.sh`:

```bash
cd flutter
./deploy_silent_perms.sh 192.168.1.107:5555        # 默认模式:adb 授予 WRITE_SECURE_SETTINGS,之后 app 自动自愈
./deploy_silent_perms.sh 192.168.1.107:5555 --root # root 兜底模式:排查问题或 app 自愈失效时手动修复
```

> 关键点:Android 对崩溃过的无障碍服务有退避机制,直接重新启用会被拒绝;必须"先禁用 + 删除,再启用"。脚本与 app 内自愈逻辑均已按此处理。

### 4.3 重启后自愈

- 设备重启:`BootReceiver` 收到开机广播自动拉起前台服务,并重新执行静默授权自愈;
- 服务崩溃:前台服务 `START_STICKY` 自动重启,投屏有 watchdog 线程自动重新发起;
- 无障碍被系统标记崩溃:app 启动/开机时自动 toggle 修复;仍失败时用 `--root` 模式脚本手动兜底。

### 4.4 部署验证

清空授权后冷启动,15 秒内检查 logcat 应看到:

- 投屏授权自动确认:`media, value: true`
- 无障碍就绪:`input, value: true`
- 上报成功:`host-report sn=... rustdesk_id=...`
- 投屏授权框点击授权( root 预授权时弹框仍需一次确认)

或直接从控制端发起一次连接确认可控。

## 五、控制端使用(macOS / Windows)

1. 安装控制端(CI 产物;macOS Bundle ID 为 `cn.xinzx.rustdesk.desktop`);
2. 启动后进入设备列表,点击目标设备即自动发起连接(ID、密码均按 SN 规则自动派生填充);
3. 连接成功后即为标准 RustDesk 远程桌面,可远程查看画面、注入触屏/鼠标输入、传文件等;
4. 也可从业务后台通过 deeplink 拉起:`rustdesk://connect?id=<设备ID>&password=<密码>`。

> 说明:当前控制端设备列表为本地 mock 数据,后台 API 对接留有占位(`device_register.dart` 上报暂打日志);已知单台测试设备 116 部署的仍是已撤回的新密码机制 APK(密码 `X2U6WV2K`,测试密钥),连接该设备如遇密码不符请以此为准,或用当前代码重新构建部署后恢复 SN 数字密码。

## 六、构建与打包

### 6.1 CI 构建(推荐)

GitHub Actions 工作流:`.github/workflows/build.yml`,覆盖 Android APK / macOS / Windows 三端。

- **手动触发**:Actions 页面运行 `build`,按需勾选平台(Android / macOS / Windows);
- **tag 触发**:推送 `v*` tag 自动构建(日常 push 不触发,节省配额);
- Android 签名从仓库 Secrets 读取(`ANDROID_KEYSTORE_BASE64` 等)正式签名;
- 说明:CI 的 Android 包未启用 hwcodec 特性(目标设备硬件编解码不可用,实际走 VP8 软编,功能等价)。

### 6.2 本地构建

前置:Rust 工具链、Flutter(3.24.5)、Android NDK、vcpkg 依赖(opus/libyuv/libvpx/aom 等)。

```bash
cd flutter
./build_all.sh android    # Android 被控端 APK
./build_all.sh macos      # macOS 控制端
./build_all.sh windows    # Windows 控制端(需在 Windows 上执行)
```

单平台细节参考 `flutter/build_android.sh`、根目录 `build.py`,以及 `.github/workflows/build.yml` 中的完整步骤(与 CI 等价,踩坑结论都在 CI 提交信息里)。

## 七、服务器运维

| 端口 | 用途 |
|---|---|
| 21115 / 21116(TCP+UDP) | hbbs:ID 注册与打洞协商 |
| 21117 | hbbr:中继 |
| 21114 | api-server(可选,当前未部署) |

- **资源**:hbbs + hbbr 实测内存合计约 8MB、CPU 接近 0;1 核 1GB 可带约 1000 并发中继。**唯一成本是带宽**,且仅中继时产生(P2P 直连服务器零流量):办公场景约 100KB/s,1080p 高动态最高约 3MB/s。选型参考:<50 台 → 1C1G / 5Mbps;50–500 台 → 2C2G / 10–50Mbps。
- **限速**(可选,hbbr 环境变量):`SINGLE_BANDWIDTH`(默认 128Mb/s)、`TOTAL_BANDWIDTH`(默认 1024Mb/s)、`LIMIT_SPEED`。
- 被控端资源占用(DWD68 实测):空闲约 1% CPU / 50MB 内存;受控中约 16% CPU(软件 VP8 编码)/ 72MB / 上行约 90kbps(静止画面),会话结束秒级回落。

## 八、常见问题排查

| 现象 | 原因与处理 |
|---|---|
| 连接提示 "Your ip is blocked by the peer" | 控制端出口 IP 不在白名单(§3.4)。将出口 IP 加入白名单,或经服务器中继(中继出口为 111.6.173.0/25) |
| 密码不对 / 连接要求输密码 | 密码 = 由目标设备 ID 派生的 8 位值(v2,§3.2);控制端设备列表会自动填入。确认两端 APK/桌面端为同代构建(旧"SN 数字/00000000"机制已废弃,116 等存量旧包需重装) |
| 被控端 input:false(无法远程输入) | 无障碍服务被系统崩溃退避标记拒绝。执行 `deploy_silent_perms.sh --root` 手动 toggle 修复 |
| 被控端 media:false(黑屏/无画面) | 投屏授权未放行。在被控端屏幕上点击投屏授权框("立即开始");无人值守设备用 root 模式脚本 `appops set <pkg> PROJECT_MEDIA allow` 预授权。注意:设备重启后授权框会重新弹出,需再点一次(或预授权) |
| 设备重启后连不上 | 正常应开机自启 + 自愈;若失败,重跑 `deploy_silent_perms.sh`,再检查 hbbs 注册状态(logcat 搜 `host-report`) |
| ID 变了 | ID = 业务 app 下发的 SN(归一化),SN 变更即 ID/密码变更,服务器旧记录需清理;本地缓存 SN 在重装后仍生效 |

## 九、安全注意事项(已知风险,部署前必读)

1. **密码熵不足**:密码 = SN 数字,知道 ID 即可推算密码;回落值 `00000000` 可被猜测。IP 白名单是当前主要防线,严禁将 21115–21117 端口暴露给公网任意来源;后续建议落地 `docs/sn-password-design.md` 的 HMAC 派生方案(设计已定稿,代码已撤回待重做)。
2. **设备 adb**:网络 adb 常开未认证 + SELinux Permissive 为最高危组合,量产设备必须关闭网络 adb 或启用 `ro.adb.secure=1`、SELinux Enforcing。
3. **投屏授权框需人工确认**:dewod SDK 已移除(旧版缺类不可用),投屏授权框无自动放行通道;无人值守设备务必由运维以 root 模式预授权 `appops set <pkg> PROJECT_MEDIA allow`,并留意每次重启后的一次性授权框确认。
4. **注册无认证**:hbbs 注册端点无认证,存在 ID 抢注可能;服务器端口仅对受控网段开放可缓解。
